> 版本：v2.0（2026-08-07）
> 状态：**待审计复核，复核通过后按阶段开发**
> 关联：docs/项目目录文档与业务逻辑说明.md、docs/数据库字典.md

## 一、背景与目标

### 1.1 背景

当前系统的 IT 资产管理仅覆盖服务器、域名、小程序三类，且存在以下不足：

1. **服务器字段不符合标准**：现有 `servers` 表缺少厂商、型号、序列号、RAID、网卡、硬件保修等标准信息；
2. **无虚拟化支持**：本地存在 PVE、ESXi 等虚拟化平台，一台物理机运行多台虚拟机，当前无法表达"宿主 → 虚拟机"关系；
3. **门店设备缺失**：超市行业常见的门店网络设备（网管交换机/企业级路由器/AP）、固话、电脑、电子称均无管理入口；
4. **安全边界不清**：服务器列表接口明文返回 `password`/`dbPassword`，需按内网基础防护方案收敛；
5. **统计不可靠**：首页用"列表数组长度"统计设备数，列表一旦分页，长度即失效。

### 1.2 目标

- 服务器管理升级为"物理机 + 虚拟机"统一管理，支持 PVE/ESXi 宿主下钻查看全部虚拟机；
- 新增门店网络设备、固话、电脑、电子称四类设备的完整 CRUD 管理；
- 按**内网基础防护方案**处理敏感凭据（列表不出接口、日志不记密码、不做复杂加密）；
- 首页统计走独立汇总接口，不再依赖列表长度；
- 分阶段交付，每阶段独立提交、独立测试、可独立验收。

## 二、项目安全定位（内网基础防护方案）

> 本项目是**开源的内网 IT 资产管理系统**，不是公网密码保险库，也不是多租户系统。
> 本次采用"内网基础防护方案"，**不实施** AES-256-GCM、密钥轮换、Web/EXE 密钥同步、存量密码自动迁移等复杂机制，避免过度设计。

### 密码规则（本阶段固定）

1. **数据库存储**：暂时沿用现有密码存储方式（不引入新的加密方案）；
2. **列表接口**：`GET /api/servers`（列表）**不返回** `password` 与 `dbPassword`；
3. **详情页**：保留现有内网运维查看密码的能力，**仅管理员和操作员可查看，查看者不可查看**；
4. **独立密码查看/更新接口**：`POST /api/servers/:id/password`（查看或更新），**必须单独校验角色**（管理员/操作员）；
5. **普通字段编辑**：`PUT /api/servers/:id` 不包含密码字段；密码为空表示保持原密码（密码更新走独立接口）；
6. **日志与导出**：密码**不得**写入操作日志、错误日志、Excel 导出和首页统计；
7. **代码仓库**：不允许把真实密码、`JWT_SECRET`、生产配置提交到代码仓库；
8. **适用声明**：当前方案适用于**受控内网环境**，不建议直接用于公网或多租户环境；
9. **AES 加密**：作为后续可选增强能力，**不纳入本阶段开发**。

### 服务器凭据（产品边界明确）

> 原 UI 文案"密码管理"已更名为"服务器凭据"，从 Drawer Footer 常驻按钮移入"更多"菜单。

- **定位**：服务器凭据为**内网可选明文保存能力**，用户自行决定是否录入；
- **本轮不加密**：password/dbPassword 以明文存储，**不得在任何文档或代码注释中写成"已加密"**；
- **未来可升级**：AES 加密作为后续可选增强能力，不纳入本阶段开发（§二-9）；
- **入口**：列表 Drawer Footer "更多"菜单 → "服务器凭据（可选）"；详情页顶部"更多"菜单 → "服务器凭据"；
- **弹窗交互**：默认进入设置/更新模式，不自动调用 view API；查看已保存凭据为显式二次动作；清除凭据需二次确认；
- **后端校验**：update 接口对 password/dbPassword 做类型校验，非字符串类型返回 400；
- **日志安全**：操作日志只记录"更新服务器凭据"，不记录密码值；
- **公共组件**：`ServerCredentialDialog.vue` 统一管理凭据弹窗，servers.vue 与 servers/[id].vue 共用。

## 四、服务器改造与虚拟化

### 4.1 字段变更（`servers` 表，保留云服务器能力）

新增字段（全部可空/有默认值，兼容存量数据）：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `manufacturer` | VARCHAR(50) | 否 | 厂商（戴尔/惠普/浪潮/华为/联想等） |
| `model` | VARCHAR(100) | 否 | 服务器型号 |
| `serialNo` | VARCHAR(100) | 可空 | 序列号（唯一，可空策略见 §六） |
| `raidType` | VARCHAR(50) | 否 | RAID 类型（RAID0/1/5/10/无） |
| `networkCards` | VARCHAR(200) | 否 | 网卡信息（如 `2×1G + 2×10G`） |
| `warrantyEndDate` | DATE | 否 | 硬件保修到期（与 `expireDate` 语义区分，见 §九） |
| `isVirtual` | TINYINT(1) | 是 | 是否虚拟机（0=物理机，1=虚拟机） |
| `hypervisor` | VARCHAR(20) | 否 | 虚拟化平台：PVE / ESXi / 空 |
| `hostServerId` | INT | 可空 | 宿主物理机 ID（自关联 `servers.id`，物理机为 NULL） |
| `cpuCoresAllocated` | INT | 否 | 虚拟机分配 CPU 核数（数值型，非负） |
| `memoryAllocatedGB` | DECIMAL(8,2) | 否 | 虚拟机分配内存（GB，数值型，非负） |
| `diskAllocatedGB` | DECIMAL(10,2) | 否 | 虚拟机分配磁盘（GB，数值型，非负） |

说明：
- 云服务器字段（`serverType`/`cloudAccount` 等）**全部保留**；
- 存量字符串资源字段（`cpuCores`/`memorySize`/`systemDiskSize`）保留兼容；新增分配字段用数值型；
- 自关联外键 `ON DELETE RESTRICT`；`@@index([hostServerId])`；`serialNo` 唯一索引（可空，见 §六）；
- **日期类型**：新增日期字段一律使用 `DATE`；存量 `expireDate`（VARCHAR(10)）在阶段 2A 迁移时一并转为 `DATE`（先清洗空字符串，见 §十四-日期规范）。

### 4.2 虚拟化约束（服务层统一校验，前后端一致）

| # | 约束 | 违反处理 |
|---|------|----------|
| 1 | `isVirtual=true` 时，`hostServerId` 必须指向**物理机** | 404"宿主不存在" / 400"宿主必须是物理机" |
| 2 | `isVirtual=false` 时，`hostServerId` 必须为 **NULL** | 400"物理机不能有宿主" |
| 3 | **虚拟机不能作为其他虚拟机的宿主机** | 400（同 #1） |
| 4 | 不允许服务器指向自身 | 400"不能将自己设为宿主" |
| 5 | 修改 `isVirtual` 或 `hostServerId` 时，**必须重新执行完整校验**（创建与修改共用同一服务层校验函数） | 400 |
| 6 | 删除仍有虚拟机的物理服务器返回 **HTTP 409**，禁止级联删除 | 409"该宿主机仍有 N 台虚拟机，无法删除" |
| 7 | 虚拟机分配值（CPU/内存/磁盘）必须为**非负数** | 400 |
| 8 | 创建和修改**必须使用统一的服务层校验**，不能只依赖前端校验 | — |
| 9 | 数据库层自关联外键 `ON DELETE RESTRICT` 兜底 | 409（外键约束转友好提示） |

### 4.3 服务器详情页行为（明确）

- **查看物理机**：返回宿主信息 + 该宿主下**全部虚拟机列表**；
- **查看虚拟机**：返回**宿主信息**（其所属物理机）；
- **"上一台/下一台"切换**：只针对**物理服务器**排序，不混入虚拟机；
- **新增虚拟机**：前端自动填入宿主 ID，**后端仍必须再次执行完整校验**（§4.2）；
- 详情页不展示密码明文之外的敏感字段（密码查看走独立接口，见 §五）。

## 五、敏感字段与密码策略

1. **列表接口**：`GET /api/servers` 返回体**不含** `password`/`dbPassword`；
2. **详情接口**：`GET /api/servers/:id` 返回体**不含** `password`/`dbPassword`；
3. **密码查看**：使用独立接口 `POST /api/servers/:id/password`（action=view），**单独校验角色**（仅管理员/操作员，查看者 403）；
4. **密码更新**：同一接口（action=update），仅管理员/操作员；更新后**不返回**新密码；
5. **普通编辑**：`PUT /api/servers/:id` 不含密码字段（字段白名单，见 §八-8）；密码为空=保持原密码（由"不包含密码字段"天然保证）；
6. **日志与导出**：密码不写入操作日志、错误日志、Excel 导出、首页统计；
7. **仓库安全**：真实密码、`JWT_SECRET`、生产配置不提交代码仓库（由 `.gitignore` + 部署文档约束）；
8. **内网声明**：本方案仅适用于受控内网环境，不建议直接用于公网或多租户环境（§二-8）。

## 六、可选字段、唯一索引与设备字段字典

### 6.1 可空字段策略

`serialNo`、`assetNo`、`managementIp`、`macAddress`、`phoneNumber` 等**可能为空但要求唯一**的字段，遵循：

1. **Prisma 使用可空类型**（`String?`）；
2. **前端空字符串统一转换为 NULL** 后再提交（提交层约定，后端也做一次空串→NULL 清洗）；
3. **数据库默认值不使用空字符串**（默认 NULL）；
4. **迁移前清洗历史空字符串**：把 `''` 更新为 `NULL`，再建唯一索引（MySQL 唯一索引允许多个 NULL）；
5. **迁移必须在已有数据的数据库上验证**（不能只在空库验证）。

### 6.2 唯一索引范围（决策）

| 字段 | 唯一范围 | 说明 |
|------|----------|------|
| `servers.serialNo` | **单表唯一** | 服务器序列号 |
| `network_devices.serialNo` / `managementIp` / `macAddress` | **网络设备表内唯一** | 不跨表全局 |
| `computers.serialNo` / `macAddress` | **电脑表内唯一** | 不跨表全局 |
| `computers.assetNo` / `scales.assetNo` | **各自表内唯一** | 不要求跨设备统一编号 |
| `phones.phoneNumber` | **固话表内唯一** | 号码唯一 |

说明：MAC 地址与 IP 允许在"网络设备表"和"电脑表"各存一份（两者物理上不同设备类别），**不做跨表全局唯一**；`assetNo` 不要求所有设备统一编号体系。

## 七、门店关联

1. 四类新设备统一使用 **`storeId` 外键**（`ON DELETE RESTRICT`）→ `stores.id`；
2. **门店删除被设备引用时**：API 捕获 Prisma 外键错误（`P2003`）并返回友好的 **HTTP 409**（"该门店仍被 N 台设备引用，无法删除"）；
3. **现有门店删除接口**（`DELETE /api/stores/:id`）需正确处理 Prisma 外键错误，把底层 500 转为友好 409；
4. **总部/信息部数据方案**：作为**普通门店记录**录入 `stores` 表（如名称为"总部信息部"），不新建特殊机构表；门店选择器默认展示全部门店，前端可标记特殊门店；
5. **不复制 `storeName` 到新表**（不为了兼容旧模块额外冗余）；
6. 新页面展示门店名称时，通过**关联查询 / DTO** 返回 `storeName`（联表 `stores` 取 name）；
7. **新旧模型并存**：旧模块（预算/支付等）继续用 `storeName` 字符串，新模块用 `storeId` 外键，两套模型**暂时并存**，文档明示差异，不混用。

## 八、API 契约

### 8.1 分页返回格式（统一）

```json
{ "list": [], "total": 0, "page": 1, "pageSize": 20 }
```

- 默认 `page=1`、`pageSize=20`，**最大 `pageSize=100`**；
- 排序：各列表接口在下方接口清单中明确排序字段与方向；
- 与既有 `GET /api/logs` 分页格式一致（字段名 `list`）。

### 8.2 接口清单（共 27 个，逐项列明）

> 公共参数：`page`（默认 1）、`pageSize`（默认 20，最大 100）；`keyword` 按名称/品牌/型号等模糊匹配；`status` 枚举 `正常/停用/报废`；`storeId` 精确匹配。
> 错误处理（全部接口统一）：删除不存在记录 → 404；唯一字段重复（Prisma `P2002`）→ **409**；外键冲突（Prisma `P2003`）→ **409**；参数非法 → 400。

### 8.3 通用约定

1. **PUT 字段白名单**：所有 PUT 接口显式列出可更新字段，**禁止把整个 body 直接传给 Prisma**；

3. **空字符串清洗**：可空唯一字段提交时，空字符串统一转 NULL（§六）；
4. **错误码**：400（参数/约束）、404（不存在）、403（角色不足）、409（唯一冲突 P2002 / 外键冲突 P2003 / 删除有虚拟机宿主）；

## 九、状态与提醒规则（统一）

1. **状态枚举全文统一**：`正常 / 停用 / 报废`；不使用"启用"作为资产状态；
2. **提醒对象**：只有 `status = 正常` 的资产参与保修到期与校准提醒；`停用 / 报废` 不参与；
3. **电子称校准状态**：是**计算字段**（由 `nextCalibrationDate` 与当前日期计算得出），**不与资产 `status` 混用**；
4. **`nextCalibrationDate` 为空**时不产生提醒；
5. **自然日计算**：提醒使用自然日（非工作日），**覆盖已逾期数据**（逾期 = 距离今天 ≤ 0 天，计入提醒）；
6. **服务器两个日期语义**：
   - `expireDate`：云服务器/租约到期（既有字段，语义不变）；
   - `warrantyEndDate`：本地硬件保修到期（新增）；
   - 两者各自独立参与提醒，互不覆盖；
7. **两级提醒**：距到期 ≤ **30 天** 红色、≤ **90 天** 黄色（自然日）。

## 十、首页统计口径

### 10.1 `GET /api/it-assets/summary`（本阶段固定 8 项）

```json
{
  "serverPhysicalCount": 3,
  "serverVirtualCount": 8,
  "networkDeviceCount": 12,
  "phoneCount": 25,
  "computerCount": 40,
  "scaleCount": 15,
  "expiringWarrantyCount": 2,
  "pendingCalibrationCount": 3
}
```

口径：
- `serverPhysicalCount` / `serverVirtualCount`：按 `isVirtual` 统计 `status=正常` 的服务器；
- `networkDeviceCount` / `phoneCount` / `computerCount` / `scaleCount`：各表 `status=正常` 计数；
- `expiringWarrantyCount`：**仅统计拥有 `warrantyEndDate` 字段的 `servers` 与 `computers`**（`status=正常`、自然日 ≤90 天含逾期）；
- `pendingCalibrationCount`：`scales` 中 `status=正常` 且 `nextCalibrationDate` 非空、自然日 ≤30 天（含逾期）；
- **域名和小程序继续沿用现有逻辑，不纳入本次 summary**——首页将**同时存在旧指标（服务器/域名/小程序/到期服务器）与新指标（8 项）**，文档明示避免后续误解；
- **口径统一**：服务器列表页概览卡（总数/物理机/虚拟机/即将到期）与首页服务器卡片**均采用本口径（仅 `status=正常`）**，避免"总数含停用/报废、子项只算正常"导致三卡无法相加。

### 10.2 首页图表

- 服务器图表统一采用 **"物理机/虚拟机"** 分类（柱状/占比），**不再混用 hypervisor 分类**；
- 首页只调用 summary 接口获取计数，**不拉取全部设备数据**。

## 十一、数据库迁移实施方案

### 11.1 迁移清单（按序执行）

| 步骤 | 内容 |
|------|------|
| 1 | **Server 字段扩展迁移**：加 §4.1 的 12 个新字段（含 `serialNo` 唯一索引前先清洗） |
| 2 | **Server 自关联外键迁移**：`hostServerId` 外键 → `servers.id`，`ON DELETE RESTRICT`，建 `hostServerId` 索引 |
| 3 | **四类设备表迁移**：`network_devices` / `phones` / `computers` / `scales` 各建表（含 `storeId` 外键 RESTRICT、唯一索引） |
| 4 | **索引创建顺序**：先清洗历史数据（空字符串→NULL、清理重复），再建唯一索引（避免建索引失败） |
| 5 | **历史空字符串转 NULL**：迁移脚本 `UPDATE ... SET serialNo = NULL WHERE serialNo = ''` 等 |
| 6 | **存量服务器默认值**：存量记录 `isVirtual` 默认 0（物理机）、`hostServerId` 默认 NULL、新字段默认空 |
| 7 | **迁移失败处理**：任一迁移失败立即中止，修复后重试、不跳过；**注意**：MySQL 的 `ALTER TABLE` 等 DDL 可能产生隐式提交，无法保证整份迁移脚本完全回滚——因此含数据清洗/类型转换的迁移（如 expireDate 转 DATE）必须**迁移前预检**（§11.1 步骤 1 的预检 SQL），发现无法转换的原始数据先人工修复，再执行迁移；**不自动把原始数据改为 NULL** |
| 8 | **备份**：执行迁移前**建议先备份数据库**（`mysqldump` 或 NAS 快照），生产环境强制备份 |
| 9 | **文档同步**：`schema.prisma`、`docs/数据库字典.md`、`docs/项目目录文档与业务逻辑说明.md` 同步更新 |

### 11.2 验证要求

- 迁移**必须在已有数据的数据库上验证**（非空库），不能只执行 `prisma migrate deploy` 确认无语法错误；
- 至少覆盖：存量服务器数据升级成功、多条空 `serialNo` 可共存、门店/宿主外键行为正确。

## 十四、数据库设计与迁移规范

> 目标：防止后期迁移失败。**中文注释必须落到数据库本身（migration SQL 的 COMMENT），不只是写在需求文档里。**

### 14.1 注释与一致性

1. `migration.sql` 中**表和字段都写中文 `COMMENT`**；
2. **三处一致**：`schema.prisma`（`///` 注释）、migration SQL（COMMENT）、`docs/数据库字典.md` 必须一致；
3. **验收检查**：通过 `information_schema.COLUMNS` 查询确认中文注释真实存在（不能只凭文档）；
4. 更新 `docs/数据库字典.md` 的**表总数、字段总数、表关系说明**。

### 14.2 类型与值约定

1. **统一字符集**：所有表 `utf8mb4 / utf8mb4_unicode_ci`；
2. **时间字段**：统一 `DATETIME(3)`（自动维护字段）；业务日期用 `DATE`；
3. **状态字段**：`VARCHAR(10)` 枚举 `正常/停用/报废`；
4. **主键**：统一自增 `INT`；
5. **可空与空值**：明确可空字段；**空值统一用 `NULL`，不混用空字符串**（可空唯一字段空串转 NULL，§6.1）；
6. **外键**：明确 `onDelete` 行为（本需求一律 `RESTRICT`，门店/宿主删除冲突转友好 409）；
7. **索引命名**：索引名统一（如 `表名_字段_idx`、唯一索引用 Prisma 默认名），并注释索引服务于哪个查询；
8. **唯一索引**：必须通过**已有数据迁移测试**（多条空值共存、历史重复清理）；
9. **金额/容量/费用**：明确 `DECIMAL` 精度（金额 `DECIMAL(10,2)`、容量 `DECIMAL(8,2)`/`(10,2)`）；
10. **日期字段**：**使用真正的 `DATE` 类型，禁止 `VARCHAR(10)`**；`warrantyEndDate` 等新字段一律 DATE，存量 `expireDate` 迁移时转 DATE；
11. **创建/更新时间**：新表统一含 `createdAt`、`updatedAt`（`DATETIME(3)` 自动维护；如个别表不需要 `createdAt`，在文档与 schema 中说明）。

### 14.3 迁移实施

- 迁移顺序、历史空串清洗、存量默认值、失败处理、备份要求：见 §11；
- 迁移**必须用已有数据库验证**（非空库），不能只用空库验证；验收清单见 §16-1/2。

## 十五、Windows / Docker 统一部署规范

> 目标：一套源码、两种部署（Windows EXE / Docker），运行结果一致。**Windows 和 Docker 不得各自发展一套逻辑。**

### 15.1 运行契约（两端完全一致）

1. **同一套**：API、数据库结构、Prisma migration、环境变量名称（数据库连接、JWT 密钥、端口、时区）；
2. **启动流程统一**：
   ```
   读取配置 → 检查数据库连接 → 执行 prisma migrate deploy
   → 迁移失败则禁止启动应用 → 启动 Web/API → 健康检查通过
   ```
   - 迁移失败**禁止启动**（Windows EXE 的 `StartService` 与 Docker `entrypoint.sh` 均已按此实现，本需求延续该契约）；
3. **迁移单实例**：迁移只能由一个启动实例执行，Docker **避免多副本同时迁移**（compose 用单副本 web 服务或 migration 前置 job）；
4. **版本锁定**：Docker 固定运行时版本（`node:24-alpine`）、`package-lock.json` 锁定依赖；提供 `healthcheck`；
5. **Windows EXE 依赖**：明确 Bun 是否内置（发布包 `bun/bun.exe`），缺失时给出**明确错误提示**（已有 `bunNotFoundMessage`）；
6. **持久化**：数据目录、上传文件（`data/uploads`）、日志目录（`data/logs`）使用**持久化卷/目录**（Docker bind mount / EXE 相对数据目录）；
7. **日志统一**：Windows 与 Docker 的日志格式、日志位置、时区（`Asia/Shanghai`）一致；**日志禁止记录密码、JWT、数据库完整连接串**；
8. **配置示例**：`.env.example` 提供完整配置说明，**不包含真实密码**；
9. **备份与恢复**：提供数据库备份（mysqldump）与恢复说明；
10. **冒烟测试**：Windows 与 Docker 各一套冒烟测试（登录 → 建一条记录 → 删除）；
11. **升级验证**：版本升级必须验证**旧数据库能直接迁移到新版本**（§16-2）；
12. **一致性红线**：Docker、EXE、开发环境**不得分别修改业务逻辑**（业务改动只进 `web/` 一份源码）。

## 十八、风险与说明

1. 存量 `servers.password` 维持现有存储方式，不做自动改密（内网基础防护方案，§二）；
2. 首页域名/小程序沿用旧逻辑，与 8 项新指标并存，文档已明示（§10.1）；
3. 新旧门店关联方式不同（旧 storeName / 新 storeId），两套模型并存、不混用（§七-7）；
4. 唯一索引依赖"空字符串→NULL"清洗与前端空串转 NULL 约定，前端提交层必须遵守（§六）；
5. 本方案仅适用于受控内网环境，公网/多租户部署需另行评估（§二-8）。
